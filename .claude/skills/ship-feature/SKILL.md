# Shipping a feature in Play Console Utils

Code changes alone aren't the deliverable here — this repo has docs and a
release pipeline that assume every feature lands with its surrounding
context updated. Use this checklist after writing the code, before
reporting the feature as done.

## 1. Update docs the release workflow does NOT touch

`docs/changelog.md` is auto-generated by `.github/workflows/release.yml`
from GitHub's release notes when a `v*` tag is pushed — never hand-edit it.

Everything else is manual and easy to forget:

- **`CLAUDE.md`** — add/extend an Architecture subsection for any new
  entrypoint, util, or non-obvious behavior. Follow the existing style:
  short prose, call out *gotchas* you actually hit (not what's obvious
  from reading the code).
- **`README.md`** — add a bullet under `## Features` if user-visible, and
  update any usage instructions it affects (e.g. "right-click the icon"
  wording needs to change if you add/change a popup).
- **`store-listing/DESCRIPTION.txt`** — this is the Chrome Web Store listing copy
  (Description). Add/update/remove a paragraph for any user-visible feature change.
  Plain text only — the store doesn't render Markdown/HTML,
  so don't introduce `#`/`**`/`[links]()` inside themselves.
- **`docs/privacy.md`** — update if the feature reads new data, adds a
  manifest permission or `host_permissions` entry, or changes what's
  described in the "What the extension accesses" / "Permissions"
  sections. Chrome shows permission changes to users as an install-time
  warning, so the policy needs to stay accurate. Bump "Last updated" only
  if it doesn't already say today's date.
- **`package.json` / `wxt.config.ts` descriptions** — only touch if the
  one-line summary is now actively misleading; not every feature needs this.

## 2. Manifest/permissions gotchas

- Never hand-edit a manifest — it's generated by WXT from `wxt.config.ts`
  - entrypoint declarations. Don't duplicate a field an entrypoint already
  declares (see CLAUDE.md's "Manifest is generated" section).
- **`content_scripts.matches` does NOT imply `tabs` API host access.**
  If a background script or popup needs to read `tab.url` for tabs
  matching a pattern (e.g. to decide "is this a Play Console tab"), that
  pattern must also be declared under `host_permissions` in
  `wxt.config.ts`. Without it, `tab.url` silently comes back `undefined`
  in `tabs.onUpdated`/`tabs.query` — no error, it just never matches.
  (Hit this exact bug shipping the toolbar-icon feature.)
- Reuse `utils/console-url.ts`'s `CONSOLE_URL_MATCH_PATTERN` /
  `isConsoleUrl()` instead of hardcoding the Play Console URL pattern in
  a second place.

## 3. Verify — vitest doesn't cover everything

Always run: `pnpm compile`, `pnpm lint`, `pnpm test`, `pnpm build`.

But `vitest.config.ts`'s `fake-browser` polyfill does NOT model per-tab
icon state or real popup/tab-focus semantics. Anything touching
`entrypoints/background.ts`, `entrypoints/popup/`, or the toolbar icon
needs an actual Chromium running the built extension. Pattern that works
in this sandbox (no GUI display, no Screen Recording permission):

1. `pnpm build` → `.output/chrome-mv3`.
2. Use `playwright-core` (install with `npm install playwright-core
   --no-save` in a scratch dir if not already available) with
   `chromium.launchPersistentContext(userDataDir, { headless: false,
   args: ['--disable-extensions-except=<path>',
   '--load-extension=<path>'] })`.
   - **Don't point `executablePath` at the real installed Google Chrome.app**
     — the branded build silently ignores `--load-extension` unless
     Developer Mode is toggled on in that profile's UI first, which can't
     be scripted. Point at Playwright's own cached "Chrome for Testing"
     binary instead (check `~/Library/Caches/ms-playwright/chromium-*/`
     for the exact path/version — it must match the installed
     `playwright-core` version or launch fails).
3. Grab the extension ID from `context.serviceWorkers()` (or
   `waitForEvent('serviceworker')`), then open
   `chrome-extension://<id>/popup.html` or `/options.html` directly as a
   normal tab to inspect their rendered state.
4. **Popup gotcha:** opening `popup.html` as a normal `context.newPage()`
   tab steals tab focus, so its `tabs.query({active:true,
   currentWindow:true})` sees itself, not the tab you actually want to
   test. Fix: after the popup tab loads, call `.bringToFront()` on the
   tab you want to be "active", then `popupPage.reload()` so the popup
   re-mounts and queries the correct active tab.
5. **No OS-level toolbar screenshot is available** without Screen
   Recording permission (`screencapture` fails with "could not create
   image from display"). Don't chase that — instead temporarily add a
   `console.log` in the background script at the decision point you need
   to verify, read it via `serviceWorker.on('console', msg => ...)`, and
   **remove the temporary log before finishing** (verify with `git diff`
   that no debug logging survives).
6. A URL that avoids needing real Google auth for Play Console: `https://play.google.com/console/u/0/developers`
   redirects to `https://play.google.com/console/about/` (200, public,
   still matches the `/console/*` pattern) — good enough for testing
   console-vs-non-console branching without a logged-in session.

Clean up: temp profile dirs, scratch scripts, and any debug instrumentation
belong in the scratchpad, not the repo.
